# 수동 직접 문자 발송 안전 기준

- 예약·해피콜·주간관리·재진콜의 문자 보내기는 OS 문자창/Phone Link가 아니라 `/api/sms`로 요청한다. 받는 사람과 완성 문구를 확인한 뒤 직원이 [보내기]를 눌러야 한다.
- 예약의 저장 문구 편집은 그대로 유지한다. `AppointmentSmsSend`는 `{ appointment, text, staff, onSent }`를 받는 default export다. 컴포넌트가 업체 접수 후 `markNotified`를 호출하므로 부모 `onSent`는 갱신만 한다.
- 이 변경은 `auto_notify`·`remind_enabled` 값을 변경하거나 활성화하지 않는다.

## 병원별 설정

서버는 매 요청에서 `current_clinic()`을 새로 읽고 S/N 이외는 거절한다. 해당 병원의 `SMS_SENDER_NUMBER_S` 또는 `SMS_SENDER_NUMBER_N`가 반드시 필요하다. 예전 공용 `SMS_SENDER_NUMBER`는 사용하지 않는다.

업체 키는 `SOLAPI_API_KEY_S` + `SOLAPI_API_SECRET_S`, N도 같은 접미사 쌍을 사용한다. 병원 전용 키가 모두 없을 때만 공용 `SOLAPI_API_KEY` + `SOLAPI_API_SECRET` 쌍을 허용한다. 전용 키를 일부만 넣으면 실패한다. 공용 키를 쓰더라도 병원별 발신번호는 반드시 명시해야 한다.

`GET /api/sms`는 로그인 후 설정 존재 여부만 읽는다. `설정됨`은 발신번호 승인·명의·잔액·실제 발송/도착 검증이 아니다. 번호는 SOLAPI에서 실제 발송 계정에 승인되어 있어야 한다. UI에 번호를 입력하는 것으로 등록되지 않는다. 키/발신번호 값은 응답에 노출하지 않는다.

기존 리마인더는 이번 범위에서 수정하지 않았다. 병원을 넘기지 않는 기존 `smsConfig()` 호출은 이제 설정을 반환하지 않으므로 fail-closed다. 자동문자 재개는 별도 승인/병원별 점검 없이는 하지 않는다.

## 결과와 재진콜

- 업체 접수와 환자 도착은 다르다. 성공 문구는 '업체가 발송 요청을 접수했습니다'이다.
- 네트워크 응답 유실/불명확한 업체 응답은 결과 불명으로 잠그고 재시도하지 않는다. 장부와 업체 내역을 먼저 확인한다.
- 업체 접수 후 장부/예약/업무 기록 실패는 성공+경고다. 보내지 못했다고 표시하거나 재발송을 권하지 않는다.
- 재진콜은 S만 허용한다. UI에서 최신 `assertRecontactContact`를 반복하고, API도 명시한 재진콜 행과 환자 연결·주 연락처·수신거부를 대조한 뒤 `recontact_assert_contact`를 다시 호출한다. 최초 발송이 접수된 후에만 기존 `markSent` RPC로 감사 이력을 남긴다. 실패 시 성공 이력을 만들지 않는다.
- 남은 한계: 연락 가능 검사, 외부 업체 접수, 감사 기록은 하나의 DB 트랜잭션이 아니다. 동시 직원의 한도 경쟁/접수 후 브라우저 종료까지 완전히 원자적으로 막으려면 추후 서버 예약/아웃박스와 idempotency 설계가 필요하다. 이번 변경은 자동/일괄 발송이 아니다.

## 검증

`lib/smsServer.test.ts`, `lib/sms.test.ts`는 가짜 키/번호와 모의 fetch만 사용한다. 실제 SOLAPI/DB를 호출하지 않는다. 실제 발송·배포·키 등록·설정 변경은 이 작업에서 하지 않는다.
